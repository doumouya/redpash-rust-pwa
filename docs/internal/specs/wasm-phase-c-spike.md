# WASM Phase C spike — parse on wasm

`roadmap-webassembly.md` §5 Phase C frames the spike's contract:

> "An honest perf + size delta. If the bundle is 10 MB and first-parse is
> 4 s, phase C is parked. If it's 2 MB and 200 ms, phase D follows."

The spike answers two cliff questions in §6:

1. **Polars-on-wasm binary size** when `parse.rs` becomes reachable from
   wasm-bindgen (it wasn't before — the existing 4 wrappers cover
   apply_filter / apply_sort / auto_clean / step_preview, all of which
   operate on JSON rows already in the browser).
2. **Parse-time delta** between in-browser wasm and server round-trip on
   a representative CSV.

This doc captures the measurements and the resulting recommendation.

---

## Cliff #1 — Polars-on-wasm binary size (**CROSSED**)

Added `pub fn parse_csv(bytes: &[u8]) → DemoResult JSON` to
`backend/crates/data/src/wasm.rs` (commit `e8c2226`). Rebuilt via
`sh tools/build-wasm.sh`. Bundle measurements before/after:

| Metric                          | Before     | After       | Δ              |
|---------------------------------|------------|-------------|----------------|
| raw `.wasm` (cargo build)       | 17.94 MB   | 18.23 MB    | **+0.29 MB**   |
| raw `.wasm` (post wasm-opt -Oz) | ~12.08 MB  | 11.78 MB *  | varies         |
| **over-the-wire gzipped**       | **~3.30 MB** | **3.46 MB** | **+0.15 MB**   |

\* The raw-after delta sits within wasm-opt's run-to-run noise (some
runs land smaller post-opt because dead-code elimination is path-
dependent on the input graph). The gzipped over-the-wire number is the
stable measurement and the only one that bills the visitor's network.

**Verdict: the cliff is comfortably crossed.** The roadmap's "park
at 10 MB bundle" threshold isn't in the neighborhood. The parse code
path was already largely linked because `apply_filter` /
`step_preview` etc share `parse.rs`'s `DataFrame` + polars internals;
the public `parse_csv` entry point is mostly a wasm-bindgen wrapper
over already-resident code.

### Compile spike findings — nothing broke

Built clean on first try with:

    RUSTFLAGS='--cfg getrandom_backend="wasm_js"' \
      cargo build --release --target wasm32-unknown-unknown -p data

Gus's spike-risk pre-flight (Woz.md 18:56) had `chardetng` at low risk
and `calamine` at medium risk (depending on a `default-features =
false` dance for `zip`). Both compiled clean in the existing Cargo
config. **No feature-flag friction surfaced.** This is Phase A's
groundwork paying off — `Cargo.toml`'s wasm32-only polars override
(`default-features = false`, features = `["lazy", "csv", "strings",
"dtype-full", "regex", "concat_str"]`) plus the
`[target.'cfg(not(target_arch = "wasm32"))']` gates for the
render-side deps (`maud`, `pulldown-cmark`, `syntect`, `gray_matter`)
were already in place.

## Cliff #2 — parse-time delta (**SERVER HALF FILLED · WASM HALF PENDING**)

### Server-side baseline (measured 2026-05-25 19:13 via curl)

`POST /api/demo/parse` against the 3-shape corpus generated by
`tools/wasm-bench/generate.py`:

| shape  | size      | HTTP | `parse_ms` (median, 3 iters) | total round-trip (median) |
|--------|-----------|------|------------------------------|---------------------------|
| small  | 16 KB     | 200  | 37                           | 62 ms                     |
| medium | 1.95 MB   | 200  | **1,241**                    | **2.48 s**                |
| large  | 18.70 MB  | 413  | —                            | rejected at 4 MiB cap     |

Observations:

- **Medium is slow.** ~1.24 s of pure parse on the server, plus ~1.3 s
  of HTTP transport. Total user-facing wait: ~2.5 s. This is the lane
  wasm has the most room to beat.
- **Small is trivial** — sub-100 ms total. Below this, parse-time
  measurement is noise; the harness's small.csv mostly exists to
  establish the parser's fixed-cost floor.
- **Large hits the 4 MiB demo cap** (`DEMO_MAX_BYTES` in
  `routes/demo.rs`) → 413. Real datapoint, not a bug — it's the
  "what happens when you blow the size budget" case Gus called out
  (Woz.md 18:56). The cap is intentional: an anonymous demo
  endpoint, not a real upload path.

### Wasm-side measurement — PENDING

Needs a browser. The harness is live at `http://localhost:8080/wasm-bench.html`
(commit `c340e68`). Page:

- Drag-drop or file-pick a CSV (corpus files in `tools/wasm-bench/corpus/`).
- N iterations per lane (default 3). First wasm iter includes cold
  engine load (~3.46 MB gzipped fetch + stream-compile); subsequent
  iters reuse the cached engine.
- Side-by-side table: parse-time, rows, columns, score, empty %.
- Both lanes (wasm + server) hit in one click.

Once recorded, the numbers append below as the "Cliff #2 wasm half"
table — same row shape as the server one above for direct comparison.

**Hypothesis (per roadmap §1):** medium-file wasm parse should beat
the server's ~1.24 s by:

- Zero network leg (the bytes are already in-browser).
- Rust-speed compute on the loaded buffer (same engine, same Polars
  CsvReader code path the server uses).

If confirmed (any wasm-medium parse < ~1.24 s), Phase D (full step
engine in browser) follows.

If refuted (wasm-medium parse ≥ server total, or notably worse than
server `parse_ms` alone) — Phase C is parked. Browser-side ingest
keeps the existing 40-LOC JS CSV parser in `login.js`, the wasm
engine stays at apply_filter / apply_sort / auto_clean / step_preview,
and the demo flow keeps the 5 MB ceiling.

## Bench harness as a deliverable

Per [[feedback-process-oriented]] (Gus 2026-05-25): the harness is its
own artifact, separate from this snapshot's measurements. Future
Phase D/E spikes (browser-side step engine, group_by, joins) reuse
the same generator + page shell rather than rebuilding scaffolding
each round.

What ships in `c340e68`:

- `tools/wasm-bench/generate.py` — deterministic 3-shape corpus
  (small 178×10 / medium 10 k×20 / large 431 k×5). Seed = `20260525`.
  Same seed yields same bytes; repeated runs are comparable across
  sessions.
- `tools/wasm-bench/README.md` — run instructions, corpus shape
  table, known cliffs, reusability note.
- `frontend/wasm-bench.html` — standalone page, NOT through the SPA
  router. Lives outside `partials/` because the router-loaded shell
  isn't what the bench wants (no topbar / theme / auth machinery).
- `frontend/scripts/wasm-engine.js` — `parse_csv` added to the
  engine object returned by `getEngine()`.

Adding a new bench lane (Phase D `apply_step`, Phase D `group_by`,
etc.) is a copy-paste of the wasm-lane loop in `wasm-bench.html` with
a different `engine.X()` call — the page is structured to make that
extension cheap.

## Verdict (partial)

| Cliff | Status |
|---|---|
| Size cliff (cliff #1) | **Crossed.** +0.15 MB gzipped over-the-wire is below any threshold the roadmap §5 / §6 named. |
| Perf cliff (cliff #2) | **Pending the browser run.** Server-side baseline is recorded. Hypothesis: wasm-medium parse beats server's ~1.24 s by skipping the network + Rust-speed compute. |
| Phase D unlock decision | **Pending.** Requires the cliff #2 wasm-side numbers. |

the wasm runtime's actual parse cost on a 1.95 MB CSV — which the
harness will produce in a single browser session.

## Next steps (gated on the browser run)

If wasm-medium parse < server `parse_ms` (1.24 s):

1. **Phase D unlock** — the redtable can preview cleaning steps
   client-side without a round-trip per step. Steps already have
   wasm-callable `step_preview`; the gap was ingest (now closed).
2. **Wire `login.js` demo upload to use `parse_csv` instead of the
   40-line JS parser** — single entry-point swap in `wasm-engine.js`'s
   consumers. Wire shape stays the same (Torv flagged this on Woz.md
   18:54).
3. **Bench-harness audit-row** — `rs-audit` adds a `wasm32 bundle
   size` trend row per roadmap §8. `tools/wasm-bench/` becomes the
   re-run point on each `data` crate change so size drift is visible
   in the audit history.

If wasm-medium parse ≥ server `parse_ms` (Phase C parks):

1. Document the cliff in this doc + the roadmap §6 cliffs table.
2. Phase C wrapper stays in `wasm.rs` (cheap to keep — +0.15 MB
   gzipped) for the small-file demo case, where wasm-side parse is
   trivial regardless of perf comparison.
3. Phase D blocked indefinitely on the parse-time question; revisit
   when Polars-on-wasm improves (SIMD landing, threads via
   SharedArrayBuffer + COEP/CORP rollout) or when an alternative
   parser becomes available.
