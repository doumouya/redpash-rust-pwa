# Pages

The **feature-per-page spine** — one doc per shipped page. Each documents the
page's purpose (the ONE question it answers), its rail groups/tabs, its
surface, and the business logic — written around a **generated rail
inventory** so the tab/route lists can't drift from what's shipped.

> Phase D fills these. The rail inventory region is generated by
> `doc-gen --pages` (Phase B) from `frontend/scripts/pages/*/tabs.js` +
> `main.js` ROUTES + `topbar.js` / `rail-footer.js`.

## Shared chrome

- [_shared/topbar.md](_shared/topbar.md) — logo · welcome · OmniSearch · nav
  (Home/Workspace/Cases/Monitoring) · theme · logout. Same on every page.
- [_shared/rail-footer.md](_shared/rail-footer.md) — Docs · Settings · Profile.

## The shipped pages

The 8 authed routes (from `frontend/scripts/main.js`): **describe reality, not
the target.**

- [home.md](home.md) — the user's command center. ORG group (Users / Companies
  / Teams / Memberships / Cases — **still on Home today**; CAS_274 Phase B to
  move org CRUD to the admin surface has not shipped) + DATA group (Projects /
  Files / Charts).
- [workspace.md](workspace.md) — the data surface. Rail = **Data ↔ Dashboards**
  rail-seg; main = RedTable + clean/joins/report panels.
- [cases.md](cases.md) — work tracking. Rail + **5-column kanban** (backlog →
  todo → in_progress → in_review → done) + case detail.
- [monitoring.md](monitoring.md) — platform health. Rail groups: REQUESTS /
  AUDITS / OPTIMIZATION / USERS / CATALOG (the `surface:"monitoring"` view).
- [admin-console.md](admin-console.md) — **the admin SURFACE of Monitoring**
  (not a separate page): the `surface:"admin"` rail-view, admin-gated
  (`is_platform_admin`); tabs shipped = Cleanings / Fields / Audit-catalog.
- [profile.md](profile.md) · [settings.md](settings.md) · [sheetwise.md](sheetwise.md) · [docs.md](docs.md)
